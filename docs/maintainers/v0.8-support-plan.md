## What v0.8.0-rc.1 changes

Breaking vs 0.7 (document shape genuinely differs):

- `info.protocolVersion` removed → required **root `protocolVersions`** (closed set of MCP revisions).
- `capabilities` object → **array of protocol-scoped Capabilities Objects**.
- Inline security → named root **`securitySchemes`** + Security Requirement Arrays.
- Every Tool requires an object-rooted **`inputSchema`**.
- `transports` now optional; ordinary collections must be non-empty when present.

New capabilities:

- MCP **`2026-07-28`** protocol support (stateless protocol) and multi-revision servers.
- Protocol applicability/scoping on transports, capabilities, tools, resources, resource templates, prompts.
- Deterministic **Effective Protocol Views** (projection) + conflict-detecting merge.
- Root `instructions`; formal `capabilities.extensions`.
- **Examples**: tool `examples`, tool `interactionExamples`, resource examples, prompt examples, completion examples.
- Reusable **`components`** + local **`$componentRef`** Reference Objects.
- Operation-level **elicitation declarations**.
- Object-level **`x-*`** specification extensions; **`_meta`** support.
- Primitive **`clientRequirements`**.
- JSON and restricted YAML as equally conforming serializations.

## CSP spike results

### Round 1 (2026-08-31) — `core@0.2.0` + `validator@0.4.0`: BLOCKED

Under a simulated strict CSP (`new Function`/`eval` disabled, matching
`script-src 'self'`): the bundle contained AJV's runtime `new Function`, the
**module import itself threw** (eager AJV compile at init), and even importing
only parse/serialize from core's barrel threw because it transitively pulled the
validator. Neither package was usable under the CSP.

### Round 2 (2026-09-01) — CSP packaging blockers: RESOLVED

Both upstream asks landed. Re-ran the CSP simulation (trap `new Function`/`eval`
**before** import; count codegen attempts) against each entry:

| Entry | Import | Call | Result | Codegen attempts |
|-------|--------|------|--------|------------------|
| `@mcpdesc/validator` (default) | **throws** | — | not CSP-safe (expected) | 1 |
| `@mcpdesc/validator/standalone` + `validate` | ok | ok | `valid:true` | **0** |
| `@mcpdesc/core` (barrel) + `projectEffectiveProtocolView` | ok | ok | `ok:true` | **0** |
| `@mcpdesc/core/documents` + parse/serialize | ok | ok | `parsedOk:true` | **0** |

Robustness (standalone, under CSP): a deliberately invalid doc correctly returns
`valid:false` with a `schema-validation` diagnostic (not silently passing), and a
doc with tool `examples` (heaviest interpreted embedded-schema path) validates
`valid:true` — both with **0** codegen attempts.

**Conclusion:** the editor can adopt the CSP-safe validator entry and
`@mcpdesc/core` directly under the existing strict CSP, with full structural +
semantic validation. The interim self-precompiled validator is no longer needed.
The editor **must import the `/browser` validator entry** (never the default)
and keep it out of any bundle path that would pull the AJV runtime entry. RC.1
operations use `@mcpdesc/core@0.6.1`; the earlier CSP spike established the
packaging behavior retained by current releases.

### RC.1 verification (2026-09-01) — `core@0.4.0` + `validator@0.5.0`: PASSED

A fresh published-package check exercised `RC_1_SPECIFICATION`,
`RC_1_SCHEMA_URI`, RC.1 standalone validation, Effective Protocol View
projection, and the `migrateMcpDescription07ToRc1` export with `new Function`
and `eval` blocked before import. Validation returned `valid:true` with zero
diagnostics, projection returned `ok:true`, the migration export was present,
and the test recorded **zero code-generation attempts**.

### H. Reusable components and `$componentRef` (core delivered; editor in progress)

#### Scope and boundaries

RC.1 defines five component registries under root `components`:

- `schemas`
- `toolExamples`
- `resourceExamples`
- `resourceTemplateExamples`
- `promptExamples`

`$componentRef` is a closed local reference object — RC.1's only reference
mechanism, and the concrete spelling of "local `$ref`" for MCP Description. It
must contain only a pointer matching `#/components/<namespace>/<name>`; sibling
overrides are not allowed. It is distinct from JSON Schema `$ref`: this work
resolves only MCP Description `$componentRef` values and must not fetch or
expand JSON Schema references. A document that uses JSON Schema `$ref` inside a
tool schema is out of scope and must be left untouched.

The RC.1 schema pins the shape (`src/core/mcpdesc-schema.json`, `referenceObject`):

```json
{
  "type": "object",
  "required": ["$componentRef"],
  "properties": {
    "$componentRef": {
      "type": "string",
      "pattern": "^#/components/(schemas|toolExamples|resourceExamples|resourceTemplateExamples|promptExamples)/[A-Za-z0-9._-]+$"
    }
  },
  "additionalProperties": false
}
```

References may occur in Tool `inputSchema` / `outputSchema`, declaration
`examples`, and elicitation `requestedSchema`. Component entries may reference
another entry in the same namespace. RC.1 does not allow `$componentRef` in
`interactionExamples` or `completionExamples`.

Keep ownership boundaries explicit:

- `@mcpdesc/validator/browser` remains the conformance authority. Its existing
  diagnostics cover a missing target, a wrong component namespace, and a cycle.
- `@mcpdesc/core` owns reusable, deterministic local-reference resolution.
- The editor owns source navigation and authoring UX.
- `@cisco_open/mcptoolkit-viewer` owns presentation and must not implement a
  second resolver.

#### Upstream core operation

**Delivered** in `@mcpdesc/core@0.7.0` / `@mcpdesc/validator@0.8.0`:

```ts
import { resolveMcpDescriptionComponentReferences } from '@mcpdesc/core/components';

resolveMcpDescriptionComponentReferences(document, { specification: '0.8.0-rc.1' })
// -> { ok: true, value, diagnostics, substitutions, provenance }
//  | { ok: false, diagnostics }
```

Core reuses the validator's existing `resolveComponentReferences` traversal
rather than duplicating it. Verified locally against the bundled sample: correct
resolution, source left untouched, root `components` preserved, provenance
emitted per substitution, and **zero** codegen attempts under a trapped
`eval` / `new Function`.

Verified diagnostic ownership — which layer rejects which failure:

| Case | Reported as |
|---|---|
| missing target | `missing-component-reference-target` (semantic) |
| wrong namespace for the consumption point | `wrong-component-reference-namespace` (semantic) |
| direct / indirect cycle | `component-reference-cycle` (semantic, one per participating path) |
| unknown namespace, malformed pointer, sibling keys, `components: {}` | `schema-validation` (structural — never reaches the resolver) |

Note: for a chained reference, `substitutions` counts intermediate hops while
`provenance` records only terminal substitutions, so the two legitimately differ.

The operation:

1. Validate against the exact immutable snapshot through
   `@mcpdesc/validator/browser`.
2. Return a deep-cloned resolved document without mutating the source.
3. Resolve chained references only within the required namespace.
4. Return structured diagnostics for missing targets, namespace mismatches,
   cycles, and invalid resolved values, using codes aligned with the validator.
5. Return stable provenance records containing the reference path and final
   target path, for example:

   ```ts
   {
     referencePath: ['tools', 0, 'inputSchema'],
     targetPath: ['components', 'schemas', 'searchInput'],
   }
   ```

6. Preserve the root `components` registries in the resolved clone so viewers
   can optionally expose them and source-aware consumers retain context.
7. Remain synchronous, deterministic, browser-compatible, strict-CSP safe, and
   free of file/network access.

Core tests must cover every registry and consumption point, multi-hop chains,
shared targets, missing targets, wrong namespaces, direct and indirect cycles,
invalid resolved values, immutability, deterministic provenance, Draft 4 / RC.1
selector isolation, browser bundling, and blocked `eval` / `new Function`.

#### Editor test fixtures and coverage

**Implemented.** Vitest runs via `npm run test` (jsdom, included in
`npm run prerelease`). Fixtures live in `src/core/__fixtures__/components/`,

**Valid fixtures** (validate, resolve, and render):

| Fixture | Exercises |
|---|---|
| `all-registries.yaml` | one reference into each of the five namespaces |
| `chained-schema.yaml` | multi-hop `schemas` → `schemas` chain |

| `inline-vs-ref.yaml` (pair) | referenced doc and its inline equivalent, asserted to render identically |
| `protocol-scoped-ref.yaml` | reference on a declaration filtered out by an Effective Protocol View |
| `no-components.yaml` | regression guard: inline-only document, resolution is a no-op |

**Invalid fixtures** (must fail with the expected diagnostic, leave source text
intact, and render the existing invalid-document state):

| Fixture | Expected failure | Layer |
|---|---|---|
| `missing-target.yaml` | pointer to a name absent from the registry | semantic |
| `wrong-namespace.yaml` | tool `inputSchema` pointing at `#/components/toolExamples/...` | semantic |
| `direct-cycle.yaml` | component referencing itself | semantic |
| `indirect-cycle.yaml` | A → B → A chain | semantic |
| `unknown-namespace.yaml` | `#/components/widgets/...` | structural |
| `malformed-pointer.yaml` | `#/components/schemas` / external URI / bare `#` | structural |
| `sibling-override.yaml` | `$componentRef` alongside sibling keys | structural |
| `invalid-resolved-value.yaml` | target resolves to a non-object-rooted tool `inputSchema` | structural (post-resolution) |
| `ref-in-interaction-example.yaml` | `$componentRef` where RC.1 forbids it | structural |
| `empty-components.yaml` | `components: {}` — violates `minProperties: 1` | structural |

Structural cases never reach the resolver: they surface as `schema-validation`
diagnostics, so their tests assert on that code rather than on a reference code.

Test layers:

1. **Validation** — each fixture through `@mcpdesc/validator/browser` at the
   `0.8.0-rc.1` selector; assert diagnostic codes and paths.
2. **Resolution** — each fixture through the core resolver; assert resolved
   output, provenance records, source immutability, and determinism.
3. **Rendering** — `McpDescCardView` on the `equivalent-inline` /
   `equivalent-referenced` pair yields identical markup; indicators appear only
   for resolved references and emit the expected JSON Pointer on selection.
4. **CSP** — `components.csp.test.ts` traps `eval` / `new Function` before
   importing core and asserts zero attempts.

Still outstanding: a `useDoc` reducer test asserting that `resolvedDoc`
recomputes on edit and Effective Protocol View change and that a failed
resolution never mutates `state.text`.

The bundled `examples/reusable-components.yaml` (see below) doubles as the
happy-path integration fixture; invalid fixtures stay test-only and are **not**
added to the examples menu.

#### Editor data flow

Use one source document and derive views in this order:

1. Parse source with `@mcpdesc/core/documents`.
2. Validate the unresolved source with `@mcpdesc/validator/browser` so
   diagnostics remain anchored to authored paths.
3. Apply Effective Protocol View projection when selected.
4. Resolve `$componentRef` values in the projected document through core.
5. Render the resolved result while retaining core provenance for navigation.

If resolution fails, do not render a partially substituted document. Keep the
editor source intact, show normal validator/core diagnostics, and render the
existing invalid-document state. Resolution must never rewrite Monaco content;
references remain the authored representation used by export and persistence.

#### Types and state

- Replace `components?: Record<string, unknown>` with typed component maps and
  add a discriminated `McpDescComponentReference` type.
- Update Tool schemas, declaration examples, and elicitation requested schemas
  to accept their exact inline-or-reference unions.
- Add derived `resolvedDoc` and component-resolution provenance to `useDoc`;
  keep `state.doc` as the parsed, unresolved source of truth.
- Recompute resolution after document edits and Effective Protocol View changes;
  do not add independent mutable component state.

#### Preview and navigation UX

- Render resolved schemas and examples in their existing Tool, Resource,
  Resource Template, and Prompt locations; do not add nested component cards.
- Mark resolved content with a compact linked-component indicator showing the
  component name. In the editor, selecting it navigates to the target component
  definition through `revealPathRef`.
- Keep existing example-name selection behavior. For a referenced example, the
  displayed name remains the declaration-local key while its component indicator
  navigates to the shared target.
- Add an optional collapsed **Components** section after the declaration cards,
  grouped by registry, for discovery and direct navigation. Default it to hidden
  in the standalone viewer unless a `componentDisplay` option enables `names` or
  `details`.
- Standalone viewer callbacks receive JSON Pointer strings only; editor-specific
  Monaco behavior stays in the editor adapter.
- Invalid references remain visible through validation diagnostics and must not
  produce dead navigation controls.
